# Paseo Cross-Model Root-Cause Triage & Isolated Engineering Workflow

This workflow enforces **role separation + Paseo-native managed worktree isolation + mandatory cross-model-family adversarial review**, with the critical checkpoints hard-enforced by a **Gatekeeper state machine (`scripts/flow.py`)** instead of prompt discipline alone, to eliminate symptom band-aids, single-model blind spots, and self-review rubber-stamping.

## 1. Scope & Delegated Subagent Guard

- **Pure Q&A / Status Inspection**: Answer directly. Do not create worktrees or spawn subagents.
- **Trivial Mechanical Copy Edits** (literal typo fixes or constant renames with zero causal logic): Execute and verify directly in the primary session.
- **Delegated Subagent Guard**: If running inside a child task (`PASEO_PARENT_AGENT_ID` is set, or the prompt scopes this turn to `[Triage]` / `[Explorer]` / `[Red-Team]` / `[Worker]` / `[Reviewer]`), **execute only that single role's mandate—never restart top-level coordination or spawn nested orchestration loops**.
- **Paseo Transport Discovery**: Prefer injected Paseo MCP tools (consult the `paseo` skill for runtime schema when present); fall back to the local `paseo` CLI (`paseo --help`, `paseo run --help`). If `PASEO_AGENT_ID` is absent and the user wants Paseo-tracked sessions, launch the coordinator via Paseo rather than fabricating a parent ID.

## 2. Six Specialized Roles & Cross-Model-Family Rule

Except for trivial copy edits, **the primary session never acts as both judge and production code writer**. All engineering work coordinates six distinct roles:

| Role Tag | Core Function | Workspace & Write Boundary | Deliverable | Model-Family Rule |
| :--- | :--- | :--- | :--- | :--- |
| **`Coordinator`**<br>(Primary Session) | Intent routing, run-ledger upkeep, main-checkout snapshotting, driving the Gatekeeper (`scripts/flow.py`), managed-worktree lifecycle, spawning/collecting Paseo agents, conflict-free serial merge & final integration check | Read-only anchor + conflict-free merge; **never writes feature/fix code or hand-edits merge conflicts** | Dispatch briefs, merged code & final verification report | Primary session model |
| **`[Triage]`**<br>Essence Diagnostician | Trace causal chain from symptom site `X` to root broken invariant `Y`; repo-wide sibling sweep; slice compound tasks | **Read-only bound** (no edits, no artifact-emitting builds in main checkout; verified against snapshot) | *Essence Triage & Dispatch Card* | Coordinator read-only when localized; dedicated scout subagent(s) when broad |
| **`[Explorer]`**<br>Orthogonal Explorer | Gear 2: diverge across 3 orthogonal paradigms; Gear 3: parallel outward landscape × inward hard-sample recon | **Read-only bound** | Candidate designs or landscape matrix | When `N ≥ 2` model families are online, use at most `N-1` families (reserving ≥1 distinct family for Red-Team) |
| **`[Red-Team]`**<br>Adversarial Skeptic | Falsify candidates against live source/bytecode (duplication check, unguarded bypasses, Amdahl ceiling) or run pre-mortem | **Read-only bound** | Concrete counterexamples & pruning verdict | **Must differ in model family from each candidate's authoring `[Explorer]`** |
| **`[Worker]`**<br>Isolated Implementer | `1 Worker = 1 Branch = 1 Isolated Worktree`; verify root hypothesis dynamically first (re-triage on mismatch), build root fix + counterexample tests (or PoC), and commit cleanly on the branch | **Read/write strictly inside the bound managed worktree (`--workspace <workspaceId> --cwd <wt>`) & isolated package cache**; never touch main checkout, global caches, or `git push` | Clean worktree commits, tests, raw logs | Strong coding / reasoning model |
| **`[Reviewer]`**<br>Cross-Model Auditor | Dual-lens pre-review, isolated worktree `git diff` post-review (Gear 1/2), raw PoC/benchmark data audit (Gear 2/3); `BLOCKING` requires a constructible counterexample | **Read-only bound** (inspects raw worktree files, diffs & logs directly—never summaries; worktree `HEAD` verified unchanged after review) | Graded verdict (`PASS` / `BLOCKING`) | **Must differ in model family from the corresponding `[Worker]`** |

- **Cross-Model-Family Enforcement**: Query live models first via Paseo MCP or `paseo provider ls` / `paseo provider models <provider>` to determine the count `N` of online model families (e.g., `OpenAI Codex/GPT`, `Anthropic Claude`, `Google Gemini`). **Every adversarial pair (candidate author `Explorer ↔ Red-Team`, `Worker ↔ Reviewer`) must belong to different model families** (intra-family tiers such as `Opus` reviewing `Sonnet` do **not** count as heterogeneous; fall back only if `N = 1` on the host and state that limitation explicitly). Prefer native OS read-only sandboxes when offered by a provider; otherwise enforce read-only via role prompts plus Coordinator pre/post snapshot checks on both the main checkout and target worktree `HEAD`.

## 3. Stage 00 · Mandatory Read-Only Essence Triage & Three-Gear Routing

Never classify task size by expected diff lines. Produce an **Essence Triage & Dispatch Card** before any production code edit, then **register it with the Gatekeeper** (`<skill-dir>` is the installed skill directory, e.g. `~/.paseo/skills/paseo-engineering`):

```bash
python3 <skill-dir>/scripts/flow.py --task-id <task-id> init --repo <repo-root>
python3 <skill-dir>/scripts/flow.py --task-id <task-id> triage --symptom <X> --root <Y> --gear <1|2|3> [--lenses <csv>] [--slices <csv>] [--summary <text>]
```

The triage card is no longer prose-only: `triage` rejects an empty symptom/root and rejects `X == Y` unless `--same-site-justified <reason>` is supplied, which mechanically enforces the anti-band-aid rule.

1. **Separate Symptom from Root Origin**: Pinpoint symptom site `X` vs. root invariant violation `Y`, setting the hard rule: **"Do not apply null short-circuits, exception swallowing, or symptom band-aids at `X`; fix at root origin `Y`."**
2. **Sibling Sweep & Compound Slicing**: Sweep the repo for sibling occurrences of the same root pattern; split hybrid requests into orthogonal slices with independent gears and dependencies.
3. **Route by Problem Essence** (attaching domain hard-constraint lenses as applicable: performance → [references/lens-performance.md](references/lens-performance.md); bugs/FN/FP/precision → [references/lens-bug-precision.md](references/lens-bug-precision.md); refactoring/architecture → [references/lens-refactor-arch.md](references/lens-refactor-arch.md)):
   - **Gear 1 · Fast Root Fix (Essence A: single unambiguous root omission, zero architectural ambiguity)** → **0 human stops**; `triage --gear 1` moves straight to `EXECUTION_READY`, then runs Section 4's isolated two-agent loop (`1 Isolated [Worker] + 1 Cross-Model [Reviewer]`, skipping multi-path ideation and pre-review). If build/test (`record-verify-fail`) or cross-model review (`record-review --verdict BLOCKING`) fails for **2 rounds**, or hidden cross-layer coupling surfaces, the Gatekeeper **auto-escalates to Gear 2** (`MUST_ESCALATE_GEAR2`; never merge with an open `BLOCKING` or stall in Gear 1).
   - **Gear 2 · Deep Solve (Essence B: multi-path trade-offs, cross-module/upstream library changes, strict performance/precision gates)** → Read [references/mode-deep-solve.md](references/mode-deep-solve.md) (`[Explorer]` 3-paradigm ideation → `[Red-Team]` falsification → **1 human alignment stop** → dual pre-review → parallel isolated `[Worker]`s → dual cross-model `[Reviewer]`s & data audit). Gatekeeper path: `triage` → `record-explore` → `record-redteam` → `align` → `record-prereview` → `EXECUTION_READY`.
   - **Gear 3 · Explore & Spike (Essence C: uncharted capability, `0 → 1` unproven direction)** → Read [references/mode-explore-spike.md](references/mode-explore-spike.md) (outward × inward `[Explorer]`s → `[Red-Team]` pre-mortem → **Stop 1: Spike Contract** → isolated `[Worker]` throwaway PoC + mandatory cross-model `[Reviewer-Audit]` of raw PoC data → **Stop 2: Go / Pivot / Kill**; discard raw spike and transition into Gear 2 Part 2 upon **Go**). Gatekeeper path: `triage` → `record-explore` → `record-redteam` → `align --spike-hypothesis ... --spike-samples ... --go-criteria ...` → `EXECUTION_READY` → `isolate --kind spike` → … → `decide-spike --decision go --slices <prod-slices>` (then Gear 2 `record-prereview` + `isolate --kind production`).
4. **Re-Triage**: When a `[Worker]` refutes the root hypothesis or escalation fires, run `triage ... --re-triage`; it invalidates prior explore/red-team/pre-review credentials and aligned slices, and marks every non-integrated slice `SUPERSEDED` (it can only be discarded, never merged).

## 4. Gatekeeper State Machine & Five-Step Isolated Worktree Lifecycle

### 4.1 Soft Protocol + Hard Gatekeeper

This skill is the **soft protocol** (roles, judgment, lenses). `scripts/flow.py` is the **hard gatekeeper**: a stdlib-only (Python 3.8+) state machine that atomically maintains `$PASEO_HOME/runs/<task-id>/state.json` + `status.md` (default `~/.paseo/runs/<task-id>/`, files `0600`; use `--run-dir <dir>` to override, `--paseo-home <dir>` to target a non-default Paseo home). **Run every checkpoint through the Gatekeeper; never hand-edit `state.json`.** Deterministic code, not prompt discipline, hard-blocks five classes of violation:

| # | Violation Blocked | How the Gatekeeper Enforces It |
| :--- | :--- | :--- |
| 1 | **Same-family review** (self-review rubber-stamp) | `enter-review` rejects a reviewer whose normalized model family equals the slice's `[Worker]` family; `record-prereview` / `record-redteam` apply the same rule against planned workers / explorers. A `--single-family-host` self-report is **rejected** if ≥ 2 families are live online. |
| 2 | **Uncommitted work, or unreviewed commits appended after review** | `enter-review` requires a clean worktree and `rev-list --count <SLICE_BASE>..HEAD > 0`, and refuses to resubmit the same `HEAD` that was just rejected; `record-review` re-verifies `HEAD == wt_head_sha`; `integrate` requires the worktree and the branch ref to equal `approved_head_sha`. |
| 3 | **Main-checkout tampering** (including byte edits to untracked files) | Every checkpoint compares `HEAD` **and** `main_diff_hash` (`git status -uall`, `git diff --binary HEAD`, plus SHA-256 of every untracked file's bytes and mode) to the recorded snapshot. |
| 4 | **Bypassing the 2-round cap** | `review_rounds` / `verify_fail_rounds` live in `state.json`: Gear 1 reaching 2 → `MUST_ESCALATE_GEAR2`; Gear 2/3 reaching 2 → `ROUND_CAP_REACHED`, from which only `resolve-dispute` (re-triage / discard / user-escalate) is legal. `assign-worker` is refused in those states. |
| 5 | **Merging a sick or conflicting slice, or merging `spike` / `probe` branches** | `integrate` requires `kind == production`, `state == REVIEW_PASSED`, `open_blockers == 0`, and a pinned `approved_head_sha`; it tests a conflict-free merge first and on conflict aborts to `NEEDS_REBASE` (`mark-rebased` then forces a full cross-model re-review). |

`status.md` always prints the current task/slice states and the next legal commands; `flow.py status [--json]` prints the same on demand.

**Escape hatches (bounded)**: `--re-triage` (Section 3) is the sanctioned way to change course. `--user-override "<non-empty reason>"` may skip only **workflow routing / checkpoint order** when the user explicitly says "run directly". It **never** bypasses the physical safety gates: cross-model-family pairing, a clean committed `approved_head_sha` with 0 open blockers before merge, `spike`/`probe` non-mergeability, or conflict-free merging.

### 4.2 Subcommand Map

| Phase | Gatekeeper Commands (in legal order) |
| :--- | :--- |
| Setup & routing | `init` → `triage` |
| Gear 2 / 3 discovery | `record-explore` → `record-redteam` → `align` → *(Gear 2 only)* `record-prereview` |
| Isolation & implementation | `isolate` → `assign-worker` → *(on build/test failure)* `record-verify-fail` |
| Cross-model review | `enter-review` → `record-review` *(Gear 2: lenses `A` and `B` both must `PASS` on the same `wt_head_sha`; spikes: `audit`)* → on dispute `resolve-dispute` |
| Landing | `integrate` *(on conflict → worker rebases → `mark-rebased` → fresh review)* → `verify-integration` |
| Spike / abandonment | `decide-spike --decision go\|pivot\|kill [--slices <prod-slices>]` *(`--slices` names the fresh production slices after `go`; default `<id>-prod`)* · `discard-slice` |

### 4.3 The Five Steps

Gear 1 and Gear 2 production changes execute all five steps below (Gear 3 spikes reuse Steps 1–3 for isolated experimentation and replace production code-style review with mandatory cross-model raw-data audit):

1. **Snapshot Main Checkout & Cut Paseo-Managed Isolated Worktrees (Snapshot & Isolate)**
   - `init` already recorded `BASE_SHA` and `MAIN_DIFF_HASH` (`main_diff_hash`) so pre-existing user changes stay untouched; both survive serial merges because `integrate` refreshes them.
   - Cut one branch + worktree per write slice with **`python3 <skill-dir>/scripts/flow.py ... isolate --slice <id> --branch <branch> [--kind production|spike|probe] [--backend auto|paseo|git] [--apply-dirty-patch]`**. For same-repo slices the default `auto` backend runs `paseo project create` + `paseo workspace create --isolation worktree --mode branch-off --new-branch <branch> --base <BASE_SHA>`, producing a **Paseo-native managed worktree** with its own `workspaceId`. It refuses a branch name that already exists (preventing Paseo's silent branch-rename trap), pins the base to the explicit 40-hex `BASE_SHA` (never the literal `HEAD`), verifies the new worktree's branch/`HEAD`, and records `workspaceId`, `cwd`, and `slice_base`. Only when the target is an external repo, or Paseo is absent / its daemon unreachable, does `--backend auto` fall back to `git worktree add -b <branch> <dir> <BASE_SHA>` (`--backend paseo` fails hard instead).
   - `kind` is bound to the gear: `production` only in Gear 1, or Gear 2 `EXECUTION_READY` for aligned slices; `spike` only in Gear 3 `EXECUTION_READY`; `probe` (disposable micro-probe) only in Gear 2 `EXPLORED`/`FALSIFIED`.
   - If the task explicitly depends on uncommitted main-checkout edits, pass `--apply-dirty-patch`: the patch is committed as a standalone baseline commit inside the worktree, `SLICE_BASE` moves to it, and its SHA-256 is pinned so review diffs isolate `[Worker]`'s own changes. Merging such a slice later requires `integrate --into-worktree <clean-worktree>`—never silently commit user changes in the dirty main checkout. Whenever any command writes package caches (`mvn install`, `pip install`, or upstream library builds), configure an isolated local cache (`-Dmaven.repo.local`, dedicated virtualenv, etc.) so shared global caches stay untouched.
2. **Spawn Explicit Paseo Role Sessions (Dispatch)**
   - Launch each role via Paseo MCP or CLI **bound to both the managed Workspace and the physical directory**: `paseo run --no-wait -q --provider <p> --model <m> --workspace <workspaceId> --cwd <abs-worktree-path> --title "[Worker] <slice>"`. Passing only `--cwd` can leave the session attached to the parent's `workspaceId`; the dual binding closes that gap. Register the agent with `assign-worker --slice <id> --model <provider/model> [--agent-id <id>]`, which records its normalized `worker_family` and moves the slice to `IMPLEMENTING` (on Windows, explicitly `Set-Location -LiteralPath '<worktree>'` per shell call; across hosts, verify reachable workspaces/models and track `{serverId, agentId, workspaceId, cwd}`).
   - Include in every brief: acceptance criteria, the *Essence Triage & Dispatch Card* (root `Y` + anti-band-aid rule), active `lens-*.md` paths, editable file scope, and verification commands.
3. **Verify Hypothesis → Implement at Root → Counterexamples → Commit (Implement & Commit)**
   - **`[Worker]` Right to Challenge**: First verify the dispatch card's causal chain with a minimal test or probe; if dynamic evidence refutes the static diagnosis or changing `Y` breaks caller contracts, **stop immediately and return empirical evidence to re-triage** rather than forcing broken edits.
   - Implement the root fix, sibling fixes, and automated counterexample/regression tests inside the isolated worktree, and create clean local Git commit(s) on the slice branch with zero untracked build residue. Failed build/test rounds are logged with `record-verify-fail --slice <id> --summary <text>` (Gear 1: 2 rounds ⇒ `MUST_ESCALATE_GEAR2`).
4. **Commit-Completeness Gate & Cross-Model Raw-Diff Audit (Cross-Model Review)**
   - **`enter-review --slice <id> --reviewer-model <provider/model> [--lens default|A|B|audit]`** is the Coordinator's pre-snapshot: it verifies (1) main checkout matches `HEAD` + `main_diff_hash`; (2) `git -C <wt> status --porcelain` is empty; (3) `git -C <wt> rev-list --count <SLICE_BASE>..HEAD > 0`; (4) reviewer family ≠ worker family; (5) `HEAD` ≠ the last rejected `HEAD`; and records `wt_head_sha`. Gear 2 adds the second lens (`--lens B`) on the **same** `wt_head_sha`.
   - Launch a **cross-model-family read-only `[Reviewer]`** (bound with `--workspace <workspaceId> --cwd <wt>`), passing only the isolated worktree path, `git diff <SLICE_BASE>...HEAD`, raw test log paths, and **neutral review questions** (never biased summaries).
   - **`record-review --slice <id> --verdict <PASS|BLOCKING> --blockers <n> [--lens ...] [--counterexample <text>]`** is the post-snapshot: it re-verifies `HEAD == wt_head_sha`, a clean worktree, and an untouched main checkout, so an unsandboxed reviewer cannot mutate `<wt>`. `BLOCKING` requires `blockers ≥ 1` and a non-empty constructible counterexample (otherwise it is `OPTIONAL`).
   - **Closure & 2-Round Cap**: Route valid `BLOCKING` defects back to the isolated `[Worker]` (`CHANGES_REQUESTED`) to commit fixes, then have the **same cross-model `[Reviewer]` audit both the incremental fix and the full `git diff <SLICE_BASE>...HEAD`** via a fresh `enter-review` until `0 BLOCKING`:
     - **Gear 1** hitting **2 unresolved rounds**: the Gatekeeper auto-escalates to **Gear 2**;
     - **Gear 2** hitting **2 unresolved rounds** (`ROUND_CAP_REACHED`): use `resolve-dispute --action re-triage|discard|user-escalate --reason <text>`. A dispute is never silently turned into `PASS`: downgrade to `OPTIONAL` only through a recorded refutation when the Reviewer failed to supply a constructible counterexample (log it in `status.md`), escalate genuine architectural trade-offs to the user (`AWAITING_USER_RULING`), or **re-triage / discard the candidate slice** if real defects remain unfixed—**never merge while a valid `BLOCKING` counterexample remains open**.
5. **Conflict-Free Serial Integration, Final Verification & Cleanup (Integrate or Discard)**
   - **Coordinator never hand-edits merge conflicts**: **`integrate --slice <id> [--into-worktree <clean-wt>]`** merges serially only after **tests pass + cross-model review reached `REVIEW_PASSED` (`0 BLOCKING`, pinned `approved_head_sha`) + active lens gates pass**. It prefers `--ff-only`; otherwise it dry-runs `merge --no-commit --no-ff` and, on conflict, aborts and sets `NEEDS_REBASE`. The Coordinator must **not** resolve code conflicts manually—send the slice's `[Worker]` to `rebase` onto the new target tip inside its worktree, resolve conflicts + re-run tests, then run `mark-rebased --slice <id> --new-slice-base <sha>` (which wipes the prior approval and returns the slice to `IMPLEMENTING`) and pass a full cross-model re-review before integrating. If the main checkout has uncommitted user files, in-place merge is rejected: deliver through `--into-worktree` or ask the user.
   - When every aligned slice is `INTEGRATED`, the task enters `MERGED_PENDING_VERIFY`. Run **`verify-integration --cmd "<test-or-build-command>"`** on the final merged tree: only on exit code `0` does it run `paseo workspace archive <workspaceId>` (or `git worktree remove`) for each integrated slice, confirm the directories are gone, delete the temporary local branches (`git branch -D`), and mark the task `COMPLETED`.
   - If empirical targets fail, a slice is abandoned, or a spike is killed, archive evidence/reviews first, then run `discard-slice --slice <id> --reason <text>` (or `decide-spike`, which archives the workspace and deletes the `spike/probe` branch) to remove the managed workspace/worktree and branch cleanly.

## 5. Resilience, Load Mutual Exclusion & Safety Boundaries

- **Heavy-Load Mutual Exclusion**: Reading code, static reviews, and isolated worktree coding may run in parallel (2–3 active subagents typical); **full test suites, heavy builds, and benchmarks must check host load and run serially or core-pinned**.
- **On-Disk Run Ledger & Quota Failover**: The Gatekeeper persists `$PASEO_HOME/runs/<task-id>/state.json` (machine truth) and the auto-rendered `status.md` (default `~/.paseo/runs/<task-id>/`) from `init`: dispatch card, Paseo agent IDs/models, `workspaceId` ↔ worktree map, round counters, passed gates, and next legal commands; add evidence paths in the `--summary` fields. On restart or resume, run `flow.py status` and read the ledger first—never redispatch finished work. Await completion notifications (`paseo wait` / MCP wakeup) rather than tight polling; fail over immediately to an alternate model family upon quota exhaustion or heartbeat timeout (the new reviewer/worker is re-checked against the family gate).
- **Gatekeeper Is Authoritative**: If the Gatekeeper rejects a command, fix the underlying condition (commit, re-review, rebase, switch model family)—never edit `state.json`, never fabricate flags, and never reach for `--user-override` unless the user explicitly authorized skipping workflow order. No Paseo (or Python) runtime: follow the same checkpoints manually and state in the final report that the hard gates were not machine-enforced.
- **External Side-Effect Gate & Pitfall Distillation**: Subagents must never run `git push`, create/edit PRs/MRs/issues, delete external branches, deploy, or message externally (reserved for the Coordinator under explicit current-session authorization). Suggest a one-line `AGENTS.md` pitfall entry only when a counterintuitive repo-wide trap was uncovered, and report root cause, branches/worktrees, participating Paseo role agents/models, executed tests, and unexecuted checks honestly.
