# 缺陷与精度治理专项卡（Bug & Precision Lens）

处理疑难 Bug 修复、崩溃/死锁排障、静态/动态分析漏报（FN）与误报（FP）治理、数据一致性错误等任务时强制挂载。

## 1. 因果链实证与红绿复现先行（Red-Green Gate）

- **先复现后动刀**：修改业务代码前，优先构造最小可复现用例或自动化单元测试，确认其在修改前**因预期根因稳定失败（红灯）**，修改后**稳定通过（绿灯）**。
- **不可稳定复现时的诚实边界**：对极端并发时序、外部环境依赖等无法稳定复现的偶发问题，必须给出完整的静态状态流转证明与日志证据，并在最终报告中明确标注“未获动态确定性复现”的验证限制，不得伪称已复现。

## 2. 严禁表象贴膏药（Root Invariant Enforcement）

- 沿着数据流/控制流逆向定位**设计不变量第一次被破坏的位置**：
  - 若上游生产了非法状态/空引用/错误建模，必须在上游构造或转换契约处修复（或明确合法化其领域语义）；
  - **严禁**在下游报错消费点仅加空指针短路、宽泛 `try-catch` 吞异常或针对单一测试样本硬编码名称/常量特判来掩盖脏状态。

## 3. 同源缺陷全仓普查（Sibling Sweep）

- 提炼本次根因的代码结构特征（如未配对释放的资源、遗漏生命周期重置的状态字段、同类 API 家族或对称的序列化/反序列化分支），在全仓做一次横向普查：
  - 低风险同源漏点在同一批次内一并修复并补齐测试；
  - 跨度过大或耦合复杂的同源项单独列明清单交协调者/用户决策，不悄悄遗漏。

## 4. 正反双向回归（防“按下葫芦浮起瓢”）

- **补漏报 / 放宽条件时**：必须同步构造结构相似但不应触发的**负向边界反例（Negative Cases）**，证明未因过度泛化引入误报或越权放行。
- **消误报 / 收紧拦截时**：必须同步运行或补充同领域**正向基准用例（Positive Cases）**，证明未因收紧条件误杀合法功能或既有检出能力。
